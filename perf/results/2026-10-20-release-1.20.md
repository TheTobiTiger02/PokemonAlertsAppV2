Device: Galaxy S21 (SM-G991B), wireless adb. Build type: `staging` (R8 + baseline profile).
Tool: `perf/app_perf.sh <label>` (atrace main-thread sections, gfxinfo, SurfaceFlinger timestats).
Map: OpenStreetMap style, street zoom in Alsbach. Live feed: 1,336–1,519 alerts.

Runs:

| Label | Code | Alerts in feed |

The map's own SurfaceView stayed at a steady 16 ms present-to-present in every run. Its stalls were all on the main thread, from the composition around it.

## Cause and fixes

- One feed filter pass took ~240 ms on the main thread (`Feed:filter` trace). The filter matcher re-normalized the same tokens (type names, areas, species) for every alert, using `java.text.Normalizer` and regex passes. It ran inside composition on every 30 s tick and on every data change. The map ran the same matcher over ~6,000 alerts.
  - Fix: memoize `normalizeFilterTokenOrNull`.
  - Fix: run feed, map and history filtering and sorting through `rememberOffMain` on `Dispatchers.Default`.
- Compass poses: the heading now updates at most ~5 Hz and only for turns of 2° or more. The heading no longer replaces the location state, so location-keyed work does not re-run on every compass update.
- Cards derive the expired and "ends before you arrive" flags with `derivedStateOf`, instead of reading the 1 s clock in their body.
- Smaller fixes:
  - The alert list equality check runs off main.
  - Category counts recount only when the alert list changes.
  - History day labels are computed once per list.
  - Spawn radii are skipped on countdown-only republishes.
  - The clustering sort parses each end time once.

Raw traces are in `.local/app-perf/<label>/` on the measuring machine (not committed).
